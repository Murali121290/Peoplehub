# PeopleHub: Test Strategy & Test Cases

This document describes the testing strategy, manual test cases for critical paths, and the guidelines for code review processes.

## 1. Testing Strategy

### Backend Testing (FastAPI)
- **Framework:** `pytest` (standard Python testing library).
- **Strategy:**
  - **Unit Tests:** Validate utilities, password checks, token decoders, and helper functions (e.g. timezone modifiers).
  - **Integration Tests:** Leverage FastAPI `TestClient` to mock database sessions, request payloads, and verify status codes and JSON schemas on API routes.
  - **Database Rollbacks:** Tests use database transaction wrapper fixtures that roll back writes on tear-down, preserving test environment purity.

### Frontend Testing (React)
- **Framework:** `Vitest` and `React Testing Library`.
- **Strategy:**
  - **Component Isolation:** Validate atomic design components (buttons, text inputs, loaders) to verify correct React rendering.
  - **Zustand Mocking:** Mock Zustand store variables to simulate different user states (Admin, Employee, Manager) without actual API handshakes.

## 2. Manual Test Cases (Critical Paths)

### Test Case 1: First-Time User Login & Force Password Change
- **Objective:** Verify default passwords trigger password change sequences.
- **Preconditions:** A user exists with password `"Welcome_PeopleHub"`.
- **Steps:**
  1. Navigate to `/login`.
  2. Input company email and password `"Welcome_PeopleHub"`. Click Login.
  3. Verify system intercepts response and displays "Please change your default password" prompt.
  4. Enter a new secure password and click Submit.
  5. Attempt to login again using the new credentials.
- **Expected Result:** Token is generated, user is redirected to the home dashboard, and default credentials no longer grant access.

### Test Case 2: Daily Attendance Punching & Break Tracking
- **Objective:** Validate check-in, check-out, and break time subtraction logic.
- **Preconditions:** Authenticated as a standard employee.
- **Steps:**
  1. On Dashboard, click **Check-In**. Verify status changes to `"Present"` and clock starts.
  2. Click **Start Break** (Lunch). Verify check-in duration pauses and break timer increments.
  3. After 1 minute, click **End Break**. Verify break duration registers.
  4. Click **Check-Out**.
- **Expected Result:** Check-in and check-out timestamps are saved. The database registers correct break durations, and `total_hours` correctly reflects elapsed time minus break minutes.

### Test Case 3: Attendance Regularization Review
- **Objective:** Ensure regularization requests are routed to manager and modify database attendance logs on approval.
- **Preconditions:** Logged in as Employee with a missing check-out date.
- **Steps:**
  1. Click **Regularize Attendance** for the target date.
  2. Enter correct check-in/out times, write a reason, and click Submit.
  3. Login as the Reporting Manager.
  4. Navigate to **Pending Requests** -> **Regularizations**.
  5. Click **Approve**.
- **Expected Result:** The attendance record status updates to `"Approved"`, regularization flags change, and total hours are updated.

### Test Case 4: Leave Flow & Balance Credit Check
- **Objective:** Ensure employees cannot apply for leaves exceeding balances.
- **Preconditions:** Employee has 5 Sick Leave days remaining.
- **Steps:**
  1. Navigate to Leave application.
  2. Select **Sick Leave** for a duration of 6 days. Click Submit.
  3. Verify UI displays error warning: "Insufficient leave balance".
  4. Re-submit for a duration of 3 days.
  5. Verify submission succeeds and balance temporarily updates.
- **Expected Result:** Validation acts as expected, and balance decreases only when request is approved by the manager.

## 3. Code Review & PR Guidelines

Before code is merged into the `main` or `release` branches, developers must follow the code review protocol:

### Branching Model
- **`main`:** Stable release branch. Direct commits are restricted.
- **`develop`:** Integration branch.
- **Feature Branches (`feature/*`):** Created from `develop`. Merged via Pull Requests (PR).

### Pull Request Checklist
- [ ] **Alembic Migrations:** PR must contain the autogenerated Alembic migration file if model tables were updated.
- [ ] **Environment Variable Updates:** Any new environment variables must be added to `.env.example` in the PR.
- [ ] **Linting & Formatting:** 
  - Python files must pass formatting reviews (`flake8` / `black`).
  - Frontend files must pass ESLint checks (`npm run lint`).
- [ ] **Approvals:** At least one senior developer must review and approve the PR.
- [ ] **Unit Tests:** Ensure code builds successfully (`npm run build` and backend test suites resolve clean).
